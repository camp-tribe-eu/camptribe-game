## Правило
Дорога модель — лише там, де помилка коштує дорожче за токени. Решта — дешевшим агентам. Головний чат
**оркеструє, а не робить** руками те, що може зробити дешевий агент.

| робота | модель агента | чому |
|---|---|---|
| оркестрація, злиття, рішення, відповіді власнику | головний чат (Opus) | контекст усієї роботи; коротко, без переказів |
| реалізація картки, фікс бага, тести до нього | **sonnet** | основний «виконавець»; добре пише код за точним брифом |
| рецензія звичайного PR (UI, контент, дрібні фікси) | **sonnet** (окремий агент, не автор) | незалежність важливіша за силу моделі |
| рецензія ядра, сейвів, детермінізму, безпеки; QA гри перед релізом | **fable** | тут дешева помилка дорого коштує (softlock, втрата сейву) |
| Jira (картки, коментарі, переходи), читання логів CI, пошук цін/фактів, оновлення документів | **haiku** або сам чат одним викликом | механічна робота; без міркувань |
| ревізія карток / аудит (рідко, раз на реліз) | **fable** | вердикт «закрити / ні» — відповідальний |

## Як не палити токени
* Fable тестує **раз на реліз**, а не на кожен коміт; фікс перевіряє дешевий рецензент, Fable — лише вибірково (ядро/сейв).
* Дрібні вади одного типу — **одна картка, один PR**.
* Бриф агенту — точний: файли, критерії, команди; «читай лише потрібні файли». Без брифу агент читає піврепозиторію.
* Головний чат не проганяє повний `npm run check` повторно, якщо агент і CI вже показали exit 0 на тому ж коміті —
  лише цільові тести + одна власна мутація (закон 7: звіт перевіряю, але не дублюю всю роботу).
* Будильники: не частіше, ніж потрібно — події GitHub і так будять сесію. Кожне пробудження головного чату з великим
  контекстом коштує недешево.
* Відповіді власнику — короткі: що зроблено, що треба від нього.

## Розбір витрат тижня 22–28.10.2026 і економ-режим (рішення власника 28.10: «цей тиждень — економ, доки не скажу інше»)
Що з'їло ліміт (тижневий ліміт головного чату дійшов до 99 %, Fable — 78 %):
1. **Головний чат робив руками.** Довгі сесії з великим контекстом: кожне пробудження перечитує весь контекст.
   Найдорожче — повторні цикли «запустив e2e → червоне → подивився лог» у головному чаті.
2. **Агенти без фактів середовища.** Агент злиття не відтворив падіння #78, бо не знав `PW_CHROMIUM_PATH` —
   прогін витрачено даремно. Бриф без фактів = агент читає піврепозиторію й вгадує.
3. **Повний набір тестів там, де досить одного spec.** Повний e2e (4 шарди) локально — хвилини й тисячі токенів логу.
4. **Побічні проєкти без межі.** Демо «Фургон мрії» — 4 версії артефакту; Canvas-версії пішли в смітник,
   бо дешевша ШІ-генерація ($1.15) дала кращий результат за одну ітерацію.
5. **Скріншоти й великі логи в контексті** головного чату: кожен лишається в контексті до стиснення.

Правила економ-режиму:
* **Головний чат:** лише бриф → вердикт → злиття → Jira. Сам не відтворює падіння, не читає логів довше `tail -40`.
* **Виконавець — sonnet; перевірка — fable** (незалежний рецензент і QA вибірково: ядро, сейв, детермінізм).
  Haiku — Jira/документи, коли треба більше одного виклику.
* **Не більше 2 агентів одночасно; ≤ 3 відкритих PR.** Одна картка = один PR.
* **Обов'язкові факти в кожному брифі агенту з e2e:** `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium-1243/chrome-linux64/chrome`,
  окремий `PW_PORT=44xx`, свій worktree, ніякого `push -f`, ганяти **лише падаючий spec** (`npx playwright test <file>:<line>`),
  повний набір — довіряти CI.
* **Чекати подію, а не опитувати.** GitHub будить сесію сам; для art.yml — один фоновий цикл очікування.
* **Візуальні ідеї — спершу дешева генерація (fal, до $1), потім код.**
* **Відповіді власнику — коротко**: зроблено / треба від тебе.
