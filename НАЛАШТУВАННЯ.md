### 2.2 Чому приватний, хоч публічний дав би безлімітні Actions

Ти сказав «нехай буде публічний, якщо Actions лімітовані» — не можу: у GDD на рядках
16020–16023 стоїть реальна родина, **George 42, Victoria 42, Matthew 15, Mia**, тобто
персональні дані, серед них дані неповнолітнього, і в публічний репозиторій це не кладеться
ні за GDPR, ні за здоровим глуздом. Ціна приватності невелика: документація «About billing for
GitHub Actions» (22.10.2026) дає на плані Free **2 000 хвилин Actions на місяць** для
приватних репозиторіїв (публічні на стандартних ранерах — безліміт), наш CI — перевірка типів,
лінт, тести й валідатор контенту — це близько півтори хвилини на прогін, тобто сотні прогонів
на місяць; Pro дає 3 000. Упремось у ліміт нескоро, а коли упремось — розділимо на публічний
код і приватний мозок. Не зараз.

### 2.3 Захист гілки `main` — спершу те, що каже документація

🔴 **На приватному репозиторії персонального плану GitHub Free захист гілок недоступний — ні
старий «branch protection», ні новий «rulesets».** Дослівно з «About protected branches»
(22.10.2026): «Protected branches are available in public repositories with GitHub Free …
also available in public and private repositories with GitHub Pro, GitHub Team, GitHub
Enterprise Cloud», і те саме по суті в «About rulesets» («Rulesets are available in public
repositories with GitHub Free … and in public and private repositories with GitHub Pro, GitHub
Team, and GitHub Enterprise Cloud»). Тобто з приватним
`camptribe-game` на Free правило «вимагати PR перед злиттям» не збережеться — замість
збереження GitHub запропонує апгрейд (точний вигляд цього повідомлення документація не описує).
Два чесні варіанти:

**Варіант А — рекомендую: підняти акаунт `camp-tribe-eu` до GitHub Pro.** Сторінка «GitHub's
plans» перелічує для Pro у приватних репозиторіях «Protected branches» і «Required pull request
reviewers», плюс 3 000 хвилин Actions замість 2 000. Ціну документацією підтвердити не можу:
github.com/pricing 22.10.2026 показує лише Free / Team / Enterprise — дивись суму на екрані
**Compare plans** під час апгрейду, перш ніж платити.

**Варіант Б — лишитись на Free без серверного захисту.** Тоді `main` тримається на дисципліні:
я ніколи не пушу в `main` напряму, все через PR і зелений CI. Це той самий стан, що на сайті,
де чотири злиття пройшли без захисту. Працює, поки в репозиторії працюю тільки я. Якщо обираєш
Б — підрозділи «Апгрейд» і «Правило» нижче пропусти.

#### Апгрейд до Pro (Варіант А) — за «Upgrading your account's plan»

1. Аватарка → **Settings**.
2. У лівому меню **Billing & Licensing** → **Licensing**.
3. Біля **Current plan** натисни **Upgrade**.
4. На сторінці **Compare plans** під **Pro** натисни **Upgrade to Pro**.
5. Під **Upgrade summary** обери щомісячну або річну оплату. Заповни **Billing information** →
   **Save**. У **Payment method** обери картку або PayPal, заповни форму → **Submit**.
6. Переглянь суму й дату списання → **Upgrade my account**.
   **Перевірка:** на сторінці Licensing біля Current plan написано **Pro**.

#### Правило для `main` через Rulesets — актуальний механізм у документації

У документації зараз два механізми: нові **rulesets** («Creating rulesets for a repository») і
старі branch protection rules — їхня кнопка тепер зветься **Add classic branch protection rule**,
слово «classic» з'явилося саме тому, що механізм вважається попереднім. Роби через rulesets;
класичний шлях — одним рядком наприкінці.

1. Відкрий `https://github.com/camp-tribe-eu/camptribe-game` → вкладка **Settings** (якщо
   вкладки не видно — випадачка **More** → **Settings**).
2. У лівому меню в розділі «Code, planning, and automation» знайди **Rulesets**. Документація
   пише «click Rulesets, then click Rulesets» — спершу пункт меню, потім підпункт; на екрані
   перший може зватися **Rules**.
   **Перевірка:** відкрилася сторінка Rulesets із кнопкою **New ruleset**.
3. Натисни **New ruleset** → **New branch ruleset**.
4. **Ruleset name:** `protect-main`.
5. **Enforcement status:** за замовчуванням стоїть **Disabled** — 🔴 перемкни на **Active**,
   інакше правило існує, але не діє.
   **Перевірка:** у полі стоїть Active.
6. У розділі **Target branches** натисни **Add a target** і додай гілку за замовчуванням або
   шаблон `main`. Точні підписи варіантів документація не наводить — потрібен той, що каже про
   default branch, або поле для шаблону, куди вписати `main`.
   **Перевірка:** у списку цілей видно `main` або «default branch».
7. У розділі **Branch protections** постав галочки (назви — з «Available rules for rulesets»):
   * **Require a pull request before merging** — число **Required approvals** лиши `0`: ти
     один, затверджувати більше нікому;
   * **Require status checks to pass** — тут обирають конкретні перевірки, а їхні назви
     з'являються у списку лише після першого прогону CI, тобто після мого пушу в Кроці 3. Тому
     зараз галочку постав, а перевірки додаси потім: повернись у цей ruleset → **Edit** → у
     цьому ж блоці додай `content` (воркфлоу `validate`) і `scan` (воркфлоу `secrets-scan`).
     Якщо список показує інші назви — бери ті, що є;
   * **Block force pushes** і **Restrict deletions** — теж увімкни, це захищає історію від
     стирання.
8. Внизу натисни **Create**.
   **Перевірка:** у списку Rulesets є рядок `protect-main` зі статусом **Active**. Справжня
   перевірка настане після Кроку 3: я один раз спробую запушити напряму в `main`, GitHub має
   відмовити, і я покажу тобі текст відмови.

Класичний шлях одним рядком: **Settings → Branches → Add classic branch protection rule →
Branch name pattern `main` → Require a pull request before merging + Require status checks to
pass before merging → Create.** Діє той самий ліміт плану, що й для rulesets.

### 4.1 Створити простір із ключем рівно `GAME`

1. Відкрий **https://utd-web.atlassian.net** під своїм акаунтом.
2. У бічній панелі ліворуч наведи курсор на **Spaces** (або **Projects**) і натисни значок
   **Create space** — плюс поруч із пунктом. Інший шлях: **Spaces → View all spaces**, там
   кнопка **Create space** угорі праворуч.
   **Перевірка:** відкрився екран вибору типу або шаблону простору.
3. Обери **Select a team-managed space** (документація: «Choose Select a team-managed space»;

4. Шаблон: **Kanban**. Залежно від екрана це або плитка Kanban → **Use template**, або під
   написом template кнопка **Change template** → Kanban.
   **Перевірка:** у підсумку на екрані видно і Kanban, і Team-managed.
5. **Name:** `CampLife Game`.
6. 🔴 **Key.** Документація: «a space key is generated for you, you can change it if you
   like». Jira підставить щось на кшталт `CG` або `CLG` — **зітри і впиши `GAME`**. Правила

8. Натисни **Next**. Далі Jira може запропонувати під'єднати репозиторії коду чи Confluence —

### 4.3 Хто на сайті адміністратор — і хто все одно бачитиме

1. Відкрий сторінку **Global permissions**: ⚙ праворуч угорі → **System** → **Global
   permissions**. Назву сторінки документація підтверджує, шлях у меню — ні; якщо не знайдеш —
   набери Global permissions у пошуку налаштувань.
2. Знайди рядок **Administer Jira** — там перелічені групи й люди.
   **Перевірка:** ти розумієш, хто в цих групах. Хто там є — бачитиме `GAME` попри Private.
   Якщо серед них люди з команди, яких ти там не хотів би, — прибрати їх із групи можна, але це
   зачепить їхні права на всі 66 проєктів, тому не роби цього мовчки: спершу скажи мені, кого
   саме.
3. Пам'ятай: адміністратор сайту чи організації (admin.atlassian.com) у будь-який момент може
   додати себе до `jira-administrators` — так каже документація. Від них не сховаєш.

**Навіщо окремий простір, а не мітка в CAMP:** ключ картки в коміті — це договір, і предмет
картки має збігатися зі зміненим кодом. Якщо ігрові картки підуть у `CAMP`, дошка сайту
засмітиться, а я перестану розрізняти, що чиє.

## Крок 5. Другий акаунт — у вебі

Ти правий, що в десктопному застосунку дві сесії різних акаунтів одночасно не тримаються.
Тому гра живе у **вебі**, і я перебудував усе під це.

Звірено 22.10.2026 з документацією Claude: «Get started with Claude Code in the cloud», «Use
Claude Code in the cloud», «Configure cloud environments», «Manage members on Team and
Enterprise plans», «Purchase and manage seats on Team plans», «Use Claude Code with your Team
or Enterprise plan», «Use the Connectors Directory», «Verify your phone number», «Log in to
your Claude account», «Find and join a Team or Enterprise organization»; і GitHub:
«Installing a GitHub App from a third party», «Using secrets in GitHub Actions».

### Три факти з документації, перш ніж починати

* **Телефон.** Для кожного нового акаунта Claude потрібне підтвердження номера SMS-кодом,
  обійти не можна. **Один номер може підтвердити до трьох акаунтів** — твій другий акаунт у
  ліміт вкладається. VoIP, Google Voice, стаціонарні номери не приймаються.
* **Місце.** Claude Code входить у **кожне** місце Team-плану; хмарні сесії (claude.ai/code)
  доступні на Team. Premium-місце дає лише більше ліміту використання — для старту не треба.
* **Домен.** Запросити можна лише адресу з **дозволеного домену** організації. Твоя Team
  створена на домені UTD, не на `camptribe.eu`, тому домен спершу треба додати — це 5.1,
  пункт 1.

### 5.2 Новий акаунт — в окремому вікні браузера

1. Відкрий скриньку `game@camptribe.eu` і знайди запрошення від Anthropic (лист іде з
   `@mail.anthropic.com`; документація радить перевірити спам). Тему листа й назву кнопки в
   ньому документація не наводить — натисни посилання в листі. Якщо листа немає через кілька
   хвилин — під головним акаунтом **Organization settings → Members** і надішли запрошення
   повторно (документація: resend там само).
2. На claude.ai обери **Continue with email** → впиши `game@camptribe.eu`. Прийде лист
   із темою **«Secure link to log in to Claude.ai»** — натисни посилання на тому самому
   пристрої (з іншого пристрою посилання видасть код, який треба ввести там, де ти починав).
   **Перевірка:** claude.ai відкрився, вгорі або внизу — ім'я нового акаунта.
3. Підтверди телефон: впиши номер, отримай шестизначний код SMS, введи.

4. Приєднання до Team: оскільки домен дозволений і запрошення надіслане, під час реєстрації

### Що це означає і чого коштує

🔴 **Веб-сесія не бачить твій Mac.** Документація: «Uses your local config: No, repo only». Ні
файлів, ні `secrets.env`, ні локальної БД. Тому вся інфраструктура перенесена в репозиторій:
мозок, закони, скіли, процеси, конвеєр генерації. Один клон — і в нього є все.

Браузерній грі ноутбук і не потрібен. Але є наслідок: **ключі живуть у секретах GitHub**, а не
в чаті. Генерація арту йде через `Actions → art`, і ключ не бачить ні чат, ні репозиторій.

**Перевірка кроку 5:** він має сам сказати, що перший код — валідатор контенту, а не сцена
Phaser, і що арт береться з Kenney CC0, а не генерується. Якщо запропонує почати з Phaser —
він не прочитав конституцію, скажи перечитати.
